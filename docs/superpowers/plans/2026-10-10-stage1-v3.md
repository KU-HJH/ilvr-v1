## 실행 경계, 기존 증거와 공통 명령

이 계획은 승인된 architecture의 구현 계획이며 아직 제품 구현 승인이 아니다. 사용자 검토와 전체 구현 방식 선택 후 실행한다. 이전 native 선택은 CPU probe에만 적용되었다. 계획 내 인터페이스가 연속적으로 연결되므로 root native 구현 후 독립 최종 검토를 권고한다. Subagent-driven을 선택하면 그 skill의 task별 implementer/reviewer/fixer와 최종 검토를 그대로 적용한다. Native에서도 독립 specification/quality review를 생략하지 않는다.

Task 1–10의 코드·CPU 검증과 제한된 분산 acceptance 준비가 구현 범위다. Task 10에 명시한 실제 training acceptance 실행은 해당 bounded 실행이 승인된 경우에만 한다. 전체 데이터 학습과 TEST400 성능 측정은 이후 실행 작업이며 이번 계획 작성이나 일반적인 준비 완료에 포함하지 않는다. 이 경계를 새로운 조기 성능 보장으로 해석하지 않는다.

기존 v2 scratch의 26 CPU tests와 13 positive matrix cases는 작은 alias/checkpoint 실행의 증거다. 제품 구현을 검증한 결과가 아니다. 현재 전체 CPU suite는 native-root import에서 6 collection errors로 실패한다. Task 1/2에서 원인을 수정하며 과거 실패 기록을 유지한다.

각 task의 RED/GREEN 명령에서 아래 shell 함수 P를 사용한다. 실행 시 task별 고유 TAG를 지정한다. 체크포인트를 쓰는 테스트도 이 tmp 안에만 저장한다.

~~~bash
export PYTHONDONTWRITEBYTECODE=1 OMP_NUM_THREADS=1
export PYTHONPATH=transformers/src:src:.
export CUDA_VISIBLE_DEVICES=''
P() {
  mkdir -p "checkpoints/workflow-validation/stage1-v3/$TAG/tmp"
  TMPDIR="$PWD/checkpoints/workflow-validation/stage1-v3/$TAG/tmp" \
    ./venv/ilvr-venv/bin/python -m pytest -q -p no:cacheprovider \
    --basetemp="checkpoints/workflow-validation/stage1-v3/$TAG/pytest" "$@"
}
~~~

사전에 checkpoints symlink 목적지가 canonical storage인지 확인한다. 출력은 logs/stage1-v3-implementation/<task>/에 저장한다. 아래 test code는 named fixture를 사용하는 핵심 assertion이다; fixture는 같은 test 파일 또는 명시한 tests/stage1/v3_helpers.py에 만들며 제품 함수를 복제한 oracle은 금지한다. RED는 새 assertion의 원인으로 실패해야 한다. 이미 통과하는 기존 회귀 테스트는 RED로 가장하지 않는다. 각 commit은 해당 task Files의 실제 변경만 stage한다.
